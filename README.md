# Delhivery Last-Mile Delay Intelligence Pipeline

**Program:** Artificial Intelligence and Machine Learning Certification · E&ICT Academy, IIT Roorkee  
**Deliverable:** Single public GitHub repository on `main`

This repository answers three operational questions for a regional Delhivery team using only the synthetic data generated by `generate_data.py`:

1. How long will a parcel really take? (regression)
2. Which parcels will miss their promise? (classification + alert threshold)
3. Which hubs need which playbook? (K-Means segments)

Cleaning and feature code written in Part A is reused by every later stage. The final scoring script combines the classifier probabilities with hub segments to produce a concrete action list for new parcels.

---

## How to run

From a fresh clone:

```bash
pip install -r requirements.txt
python generate_data.py          # writes data/hubs.csv, raw_shipments.csv, new_shipments.csv
python part_a_clean_eda.py       # writes data/modelling_table.csv + Part A outputs
python part_b_regression.py      # regression models + metrics
python part_c_classification.py  # classifier, threshold, feature selection
python part_d_segments.py        # hub profiles + K-Means segments
python package_model.py          # builds models/delay_model.pkl and helpers
python predict_delay.py          # scores the 48 new shipments → outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is regenerated by `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`. Graders should re-run `package_model.py` when installed versions differ.

Pinned versions used:

```

numpy==2.4.4
scikit-learn==1.9.1
joblib==1.6.0
```

## Data findings

All numbers below are taken from the CSV files written by `part_a_clean_eda.py`.

1. **Service type most delayed.** Express parcels are delayed most often: **delay rate 0.4897** (119 of 243). Standard is 0.2056 and Economy only 0.0857 (`outputs/part_a_delay_by_group.csv`).

2. **Tier effect.** Delay rate rises sharply with hub tier: Tier 1 = **0.0400**, Tier 2 = **0.2150**, Tier 3 = **0.4400**.

3. **Distance bands.** Delay rate climbs with distance: 0-200 km = **0.0219**, 201-400 = **0.1368**, 401-600 = **0.4364**, 601+ = **0.8523**.

4. **Strongest correlates of `delivery_hours`.** Ranking absolute correlation and excluding the target itself:  
   - `promised_hours` **+0.8372**  
   - `distance_km` **+0.4013**  
   - `n_stops` **+0.3247**  
   (`outputs/part_a_correlations.csv`)

5. **Why log-transform declared value.** The median-filled `declared_value_inr` has mean **1533.05** but median only **1121.5** (right-skewed). After the natural log the mean and median become almost identical (**7.028** vs **7.022**), stabilising the feature for linear models.

Overall delay rate on the 1,200 clean shipments is **0.2317** (278 delayed). After cleaning there are zero missing values in the 17 features plus targets.

## Model results (regression)

From `outputs/part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv` and `part_b_cv.csv`.

- **Baseline R² (validation) = −0.0212.** Predicting the training-set mean of delivery hours explains essentially nothing; any useful model must beat this.
- **Winning model on validation:** Linear Regression (RMSE **4.8912** hours, R² **0.9313**). Gradient Boosting was a very close second (RMSE 4.9165, R² 0.9306). Final test R² of the linear model = **0.9493**.
- **Tree depth bias/variance.** Depth 1 shows high bias (val RMSE 12.13, gap to train only ~0.5). Unlimited depth shows high variance (train RMSE 0.00, gap to val ≈ 7.79). Best validation depth was **6** (val RMSE 6.28).
- **Learning-rate experiment.** lr = 0.1 gave the best validation R² (**0.9306**). lr = 0.01 under-fits (R² 0.7127 — too slow). lr = 1.0 overshoots (R² 0.8440).
- **Cross-validation.** On the combined 1,020 train+val rows both top models stay above 0.92 mean R² with std < 0.01. Although CV slightly prefers Gradient Boosting, the single validation ranking selected Linear Regression; either is shippable. We kept the validation winner (Linear Regression) for the reported test score.

## Model results (classification)

From `outputs/part_c_models.csv`, `part_c_feature_scores.csv`, `part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv` and `part_c_final_test.csv`.

- **Blind baseline accuracy = 0.7667** (always predict “on time”). It never catches a delayed parcel (recall = 0), so it is useless for operations.
- **Noise columns.** The five bookkeeping columns together hold ~0.22 of Random-Forest importance. All five rank outside the top 7 by F-score (F-scores < 10 while the top-7 minimum is > 30). The exact top-7 by F-score are: `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`.
- **Select-K table.** Validation F1 peaks at k = 7 (**0.8333**), confirming that dropping the noise columns improves the forest.
- **Tuning.** On the 180-row validation set the untuned forest on the same 7 features (val F1 **0.8333**) beat both GridSearchCV (0.775) and RandomizedSearchCV (0.7848). With such a small validation set, exhaustive tuning can over-fit the validation slice; we therefore kept the default forest on 7 features.
- **Alert threshold.** Operations rule: highest threshold whose validation recall ≥ 0.80. That threshold is **0.5** (val precision 0.7955, recall 0.8333).
- **Test performance** (41 delayed parcels): precision **0.6889**, recall **0.7561**, F1 **0.7209**. Test recall is modestly lower than validation recall, as expected with only 41 positive cases.

## Operations recommendation

**Escalate segment hubs** (delay rate 0.46): the nine hubs whose real operating behaviour is most stretched. Their average delivery hours are 64.65 and mean distance ~470 km.

**Tier-label mismatches** (`outputs/tier_vs_segment_mismatch.csv`):

| Hub   | City      | Official tier | Actual segment |
|-------|-----------|---------------|----------------|
| HUB07 | Kolkata   | 1             | Watch          |
| HUB13 | Nagpur    | 2             | Escalate       |
| HUB15 | Kochi     | 2             | Escalate       |
| HUB22 | Dehradun  | 3             | Watch          |

These four hubs should **not** be managed purely by their official tier label; the segment (especially Escalate for Nagpur and Kochi) should drive the playbook.

**Alert threshold = 0.5.** From the test evaluation: of every 10 flagged parcels roughly **7** are truly delayed (precision ≈ 0.69); of every 10 delayed parcels roughly **8** are caught (recall ≈ 0.76).

**New-parcel batch (48 shipments):** 8 parcels were flagged; **6** of them require an immediate “Escalate to hub manager” action because they belong to Escalate-segment hubs; the other 2 receive a proactive customer call.

**Why keep K = 3.** Separation ratio rises from 2.89 (K=2) to 5.39 (K=3) to 6.30 (K=4) to 6.89 (K=5). However K = 4 and K = 5 each produce at least one cluster smaller than 6 hubs. Operations runs exactly three playbooks; a segment of 2–4 hubs is too small to own its own playbook, so K = 3 is the practical choice.

## Production plan

**(a) Production-readiness mapped to this repository**

| Characteristic     | Concrete item in repo                                      |
|--------------------|------------------------------------------------------------|
| Accuracy           | Test F1 / RMSE reported in `part_c_final_test.csv` / `part_b_metrics.csv` |
| Reliability        | `part_d_reload_check.csv` proves pickle round-trip (diff ≤ 1e-9) |
| Reproducibility    | Fixed random_state values + pinned `requirements.txt` + deterministic scripts |
| Maintainability    | Shared `src/shipment_prep.py` used by training and scoring |
| Consistency        | Same `clean_shipments` + `build_features` + median impute values for train and new data |
| Monitorability     | `outputs/new_shipment_actions.csv` + weekly metrics listed below |

**(b) Quantities to monitor (with triggers)**

1. Weekly delayed share of delivered parcels — alert if > 0.28 (≈ +20 % above the historical 0.23).
2. Weekly share of parcels flagged by the model — alert if outside [0.10, 0.25].
3. Recall measured on parcels whose outcome is now known — alert if falls below 0.65 for two consecutive weeks.

**(c) Retraining schedule & sale-event handling**

- Retrain every 4–6 weeks or after any major network change (new hubs, route redesign).
- The 15–28 September sale window (`sale_event_flag`) must be evaluated against **other sale windows**, never against ordinary weeks; otherwise the model will learn an inflated baseline delay rate.
- Data drift would appear as a sustained rise in the residual of the regression model, a drop in classification recall, or a change in the distribution of `distance_km` / `n_stops` relative to the training medians stored in `models/impute_values.csv`.

## Limitations

1. **Synthetic data.** All rows are generated by the provided script; real Delhivery operational noise, scanner failures and customer behaviour are not present.
2. **Small positive class in the test set.** Only 41 delayed parcels appear in the held-out test split, so precision/recall estimates have wide uncertainty.
3. **Single validation split for threshold selection.** The 0.5 threshold was chosen on one 180-row validation slice; a different random split could move the operating point.
4. **K-Means assumes spherical clusters.** The three operating segments are useful for playbooks but do not capture every nuance of hub behaviour (e.g. seasonal monsoon effects beyond the binary rain flag).
